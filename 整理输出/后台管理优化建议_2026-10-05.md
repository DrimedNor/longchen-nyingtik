# 后台管理优化建议（以「站点所有者」视角）

**日期**：2026-10-05　**对象**：`longchen-nyingtik.wiki` 管理后台（`/admin/`，零依赖单文件 SPA + `stats.longchen-nyingtik.wiki` Worker）
**视角前提**：这个后台只有**你一个人**在用（既是站长也是唯一管理员），每天大概看 1–2 次，常在手机上看；数据规模是「几十台设备、几百篇文章、上百个音频」，不是万级。所以建议的标准不是"功能全"，而是：**别让我白跑一趟、别让我看错、别让我手动算。**

---

## 零、先说结论：如果只做三件事

| 优先 | 做什么 | 为什么是它 |
|---|---|---|
| **1** | **待办闭环**：有待审核时，登录后立刻看到（顶部条 + 红点 + 直达链接） | 本次故障就是它造成的——你提交了申请，后台不显示，你根本不知道有这回事。**后台的"有事要做"必须主动喊你**，而不是等你翻到那一屏 |
| **2** | **静默失败自查按钮**（一键体检数据一致性） | 本次 bug 的本质：写入用 `user_<用户名>`、读取读 `reg_<用户名>`，**列表永远空、且不报错**。这类"看起来正常其实是坏的"必须有自检手段 |
| **3** | **概览页改成关键指标看板**（今日/7 日/30 日 + 环比） | 现在概览只有"设备数/真实/bot/管理员"四个静态计数，回答不了"最近有人在看吗、看得多不多" |

---

## 一、P0：低成本、直接减少"白跑一趟"

### 1. 待办要主动喊你（而不是静静躺在页面里）
- **现状**：概览顶部有一行 `待审核：N 个`，但它只是**一个数字**，没有颜色强调、没有跳转、不显示是谁申请的。本次你之所以没发现，正是因为这一行永远是"0"（读取端的 bug）。
- **建议**：
  - `N > 0` 时，概览顶部换成一条**醒目黄条**：`有 2 个注册申请待审核（最早 3 小时前）→ 去处理`（点击直达该模块）；
  - 侧栏/顶部放**红点数字**，进后台第一眼就知道；
  - 超过 24 小时未处理的标红（"等你很久了"）；
  - 列表默认按**申请时间升序**（最早的先处理），不要默认最新在前。
- **收益**：把"我得记得去翻"变成"它来找我"。对单人运维，这一项的省心程度最高。
- **成本**：低（纯前端；概览已有 `pendingCount` 元素）。

### 2. 一键"数据自检"（专治静默失败）
- **现状**：这次的问题本质是**两套键名**（写 `user_`、读 `reg_`），不一致时接口仍返回 `success: true` + 空数组——**没有任何报错**。同类风险还有：待审核列表里有用户但 `user_` 键已被删、已审核通过的用户仍登不上、`pending_registrations` 里残留脏 id。
- **建议**：后台加一个「🩺 数据自检」按钮，输出可读报告（每项 ✅/⚠️）：
  1. `pending_registrations` 里每个用户名是否都有对应 `user_` 键、状态是否仍为 pending；
  2. `status=approved` 的用户是否真的能登录（校验哈希存在）；
  3. 邀请码：`usedCount` 与 `usedBy` 是否一致、是否存在超额使用的码；
  4. 白名单/免密登记的设备 ID 是否仍存在对应键；
  5. 各表数据量与最后写入时间（判断"某模块是不是悄悄停摆了"）。
- **收益**：以后再遇到"后台不显示"，你自己点一下就知道是数据问题还是代码问题，不必再找我。
- **成本**：中（需要 Worker 新增一个 `/api/admin/healthcheck` 只读端点 + 前端一页报告）。

### 3. 危险操作统一"确认词 + 留痕"
- **现状**：`清理历史统计`、`清空 AI 明细`、`重算访客分类` 与「刷新列表」等日常操作**混在同一页面**，只有一句 confirm 文案；`重算访客分类` 还会实打实消耗 KV 写配额（免费版 1000 次/天）。
- **建议**：
  - 危险操作**移到页面最底部的独立「危险操作区」**，红框、说明影响范围与不可逆性；
  - 二次确认改为**输入确认词**（如清数据需键入 `清空`）；
  - 每次执行记一条**操作留痕**（时间 + 动作 + 对象 + 结果），页面顶部可看最近 10 条。
- **收益**：避免手滑清数据；出问题时能查"昨天是谁/什么操作导致的"。
- **成本**：低-中。

### 4. 错误与空状态要说人话、给下一步
- **现状**：请求失败时直接把 `网络错误：Failed to fetch` 写进表格容器（覆盖掉表格），且**没有重试按钮**；空状态只写"暂无 xxx"，不告诉你该做什么。
- **建议**：
  - 失败态：显示原因 + 「重试」按钮，而不是把错误文本当内容；
  - 空态分两种：真没有 vs 没加载出来（"未加载"要有明确提示，否则和"没有数据"长得一样）；
  - 401（会话过期）要明确提示"登录已过期，请重新登录"并给按钮——后台只有一个口令，会话过期时最容易让人以为"坏了"。
- **成本**：低。

## 二、P1：结构性改动，提升日常效率

### 5. 概览页从"计数器"变成"看板"
- **现状**：四个数字（设备总数/真实用户/爬虫/管理员），都是**累计口径**，看不出最近怎么样。
- **建议**：加时间维度与内容维度（今日 / 7 日 / 30 日）：
  | 指标 | 为什么你想看 |
  |---|---|
  | 真实访客数（有停留的） | 有没有人在真的看 |
  | 文章阅读数 / 音频播放数 | 内容消费规模 |
  | 总停留时长 | 粘性 |
  | 新增注册申请 | 增长 |
  | 待审核积压数 | 待办 |
  - 每个指标带**环比**（比上周多/少多少），并注明口径（"时长≥1 分钟计入"这类规则要写在指标旁，避免看错）。
  - **注意口径陷阱**：`管理员设备`的数据不计入全站统计（页脚已有说明）——看板上要显式标注，否则你会以为"没人看"其实是你自己的访问被排除了。

### 6. 把「设备」和「用户」两条线接起来
- **现状**：后台有两套身份，互不相通：
  - **设备**（`deviceId`，localStorage 生成）：有地理位置、浏览器、点击、时长；
  - **用户**（`username`，邀请码注册）：有账号状态、登录记录。
  - 你现在**无法回答**："这个天天来的真实用户是谁？""这个注册账号的设备都看过什么？"
- **建议**：设备列表加一列「关联账号」，显示最近一次登录该账号的设备；反过来，审核通过后给一个「查看该用户活动」入口。
- **收益**：这是把"统计"变成"能服务到人"的关键——你关心的其实不是 39 台设备，而是**两三个真人在看什么**。
- **成本**：中（Worker 侧按 username 反查设备会话）。

### 7. 任意表一键导出 CSV
- **现状**：想拿数据做分析，只能靠工作区里一堆 `analyze_daily_YYYYMMDD.py` + 手工下载的 `stats-admin-*.json`。
- **建议**：每张表右上角一个「导出 CSV」；再加一个「导出全部（设备+访客+文章+音频+点击）」。
- **收益**：临时问题（"上周谁在听什么"）不用等日报跑批。
- **成本**：低（前端生成 Blob 下载即可，无需后端）。

### 8. 排序口径与显示口径统一（这是真bug级别的体验问题）
- **现状**：时长列**按秒排序、按整分钟显示**。于是会出现「好几台设备都显示 `5 分钟`，但排序顺序不同」——刚加的点击排序会让人怀疑"是不是排错了"。
- **建议**：二选一，但必须一致：
  - 显示改成 `3 小时 12 分`（超过 60 分钟用时/分/秒），排序仍按真实秒数；**推荐这个**；
  - 或显示 `185 分`，与排序值同源。
- **附带**：同一列里混着 `-`（无数据）和数字时，建议把无数据统一排到末尾（现在按字符序，`-` 会排在最前，容易被误读成"最小"）。
- **成本**：低。

### 9. 爬虫治理（当前已有实际困扰）
- **现状**：协作日志里挂着「单 IP 注册上限第 6 天：97b3 遗留 19 台未清」——爬虫设备在"设备总数"里长期占位，稀释真实数据。
- **建议**：设备列表支持**多选 + 批量操作**（标记为"忽略/清空其统计"）；概览区分"计入统计的设备数"与"已知爬虫数"。
- **成本**：中（需 KV 批量写，注意写配额）。

## 三、P2：有余力再考虑

### 10. 移动端优先
- 设备表 12 列，窄屏只能横向拖；你在手机上看的话，每次都要横向+纵向拖动。
- 建议：<768px 时关键信息（名称/类型/时长/最近）卡片化，操作按钮固定在卡片底部（≥44px 触控区）；筛选收进抽屉。

### 11. 审核的"通过之后"
- 通过后目前只刷新列表。可考虑：给该账号发一枚**免密登记链接**（已有能力，缺联动），或显示"已通过，请用该账号在 /login 登录"。

### 12. 数据保留策略
- 设备快照/点击流水每天累积，KV 免费额度写 1000 次/天、存储也有上限。
- 建议：滚动窗口（如保留 180 天明细，更早只留聚合）+ 后台显示"当前用量/配额"进度条。

### 13. 无障碍与键盘
- 表头排序加 `aria-sort`；行内按钮触控区偏小；焦点态已在主站做好，后台沿用同一套即可。

## 四、我**不建议**做的（避免过度设计）

| 提议 | 为什么不做 |
|---|---|
| 多角色/多管理员权限体系 | 只有你一个人用，纯粹的复杂度增加 |
| 实时大屏/推送式看板 | 一天看 1–2 次，实时没有价值 |
| 引入 React/Vue 等框架重写后台 | 零依赖单文件是这个站的优势（部署简单、无构建链、git 里就一个文件）；要改就继续在单文件里加 |
| 把所有数据塞进一个"超级搜索" | 各表已有点击表头排序（09-30 上线）＋设备搜索，先把"导出"和"自检"做掉更值 |

## 五、这个后台现在最大的三个结构性问题（不解决会反复出问题）

1. **写入端与读取端各写各的键名，缺乏约束** → 本次故障的直接原因。建议定一条铁律：**一个业务对象只允许一个键前缀**（用户一律 `user_<username>`），写和读必须同时改；新增字段只加在同一个 JSON 里。
2. **一切"坏掉"的表现都是"空"** → 空列表、空统计、空状态在语义上无法区分"确实没有"和"读不到"。建议所有读取端在拼装失败时**显式抛错**，而不是静默返回空数组。
3. **后台把"看数据"和"改数据"放在同一层** → 危险动作与日常动作混排。建议分「日常区 / 治理区 / 危险区」三层，权限与视觉分级。
